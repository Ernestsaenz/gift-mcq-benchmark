# Variance / flip-rate analysis — ab520 incorrect-cell triplicates

Base directory: `data/experiment-4-aug-26/consolidate-triplicates-7-aug-26/analysis/`
Generated by `build_variance_analysis.py` from the read-only sources listed in `../SPEC.md`.
All counts below were cross-checked against SPEC.md's authoritative figures by
in-script assertions before any CSV was written (898 cells, 1796 logical calls,
1788 scored, 893/2/3 both/one/neither-replicate split, 91/2 Vertex/AI-Studio
split) — every one matched exactly.

## 1. What is being measured

Run 1 scored 6000 cells (500 questions x 3 arms x 4 models); 898 were strictly
incorrect (`strict_correct == 0`). Only those 898 cells were repeated, at run
indices 2 and 3 — the 5102 correct cells were never repeated, by design. So
this analysis cannot say anything about how often a *correct* run-1 answer
would flip to incorrect on a repeat; it only measures the wrong→right
direction. That asymmetry matters for the interpretation in §5 and is
restated in the limitations (§6).

For each of the 898 cells we ask: on run 2, and separately on run 3, did the
model get the question **right** this time (`strict_correct == 1`)? A "flip"
is a repeat run that came back correct after run 1 was wrong. We also ask,
for the 893 cells where both run 2 and run 3 were scored, whether the two
repeats **selected the same letter** — a determinism probe that doesn't
depend on which letter is correct.

## 2. Method

- **Denominators.** Every rate below is computed only over cells/runs that
  were actually scored. `flip_rate_per_run` uses `n_run2_scored +
  n_run3_scored` as the denominator (a "run-attempt" is the unit); the
  agreement rate uses `n_cells_both_runs` (a "cell" is the unit, since
  agreement is only defined when both repeats exist). Both denominators are
  written into every output CSV row — see `flip-rates-by-arm-model.csv`,
  `flip-rates-by-arm.csv`, `run2-vs-run3-agreement.csv`.
- **Confidence intervals: Wilson score interval, 95%.** Several of the
  denominators here are small (single digits to low tens for some arm x
  model slices, e.g. `openrouter_A` x gemini n=18 run-attempts, n=9 cells for
  agreement) and several counts sit near 0 or near the denominator (e.g. 0/9,
  1/1). The normal/Wald interval is a poor choice at these n — it can extend
  below 0 or above 1 and is known to under-cover near the boundaries. The
  Wilson interval stays inside [0,1] and keeps reasonable coverage at small n
  and extreme proportions, which is why it is used throughout instead of Wald
  or an exact Clopper-Pearson interval (Wilson is the more standard default
  for reporting proportions like this; exact intervals would be more
  conservative still but are not necessary here).
- **Independence caveat.** The Wilson interval, like any binomial CI, assumes
  the trials it's built from are independent draws from a fixed probability.
  That's an approximation here on two fronts: (a) questions differ in
  intrinsic difficulty, so per-question flip probability isn't constant
  within an arm x model group — some cells are "nearly gettable" and flip on
  almost any resample, others are stably wrong; (b) run 2 and run 3 of the
  *same* cell are not independent of each other in the way two different
  cells are (they share the same question, same frozen prompt, same model).
  The intervals reported here should be read as a reasonable approximate
  uncertainty band, not as precise inference under a correctly-specified
  i.i.d. model. This is exactly the kind of clustering that a mixed-effects
  or cluster-robust approach would formally account for; that refinement was
  out of scope here given the stdlib-only constraint and the sample sizes
  involved.
- **Attribution.** Per SPEC.md's rule, upstream (Vertex vs AI Studio) for
  each scored gemini_B cell is attributed by the upstream that served the
  *scoring* attempt — i.e. by following `scores.parsed_answer_id ->
  parsed_answers.provider_attempt_id -> provider_attempts.request_json`, not
  by scanning attempt history. This reproduces SPEC's 91/2 split exactly.
- **Tooling.** Python 3.14 stdlib only (`sqlite3`, `csv`, `json`, `math`).
  Database opened read-only via `file:<path>?mode=ro`.

## 3. Headline flip rates

Flip rate = fraction of scored run-2/run-3 attempts on a run-1-incorrect
cell that came back correct.

| Arm | Flips / attempts | Flip rate | 95% Wilson CI | Temp regime |
| --- | --- | --- | --- | --- |
| openrouter_A | 77 / 406 | 18.97% | [15.45%, 23.06%] | temperature_0 |
| openrouter_B | 120 / 1057 | 11.35% | [9.58%, 13.41%] | **mixed** (gemini slice only) |
| tailscale_A | 43 / 325 | 13.23% | [9.97%, 17.35%] | temperature_0 |
| **All arms pooled** | 240 / 1788 | **13.42%** | **[11.92%, 15.08%]** | mixed (see §4 caveat) |
| All arms, gemini_B excluded | 226 / 1695 | 13.33% | [11.80%, 15.03%] | temperature_0 |

(openrouter_A and openrouter_B numbers taken directly from
`flip-rates-by-arm.csv`; the two pooled rows are computed in this report by
summing `flips_run2+flips_run3` and `flip_denominator_runs` across the
relevant rows of `flip-rates-by-arm-model.csv` — provenance: ad hoc pooling
in this document, not a separate script output.)

Per arm x model (`flip-rates-by-arm-model.csv`), flip rates ranged from **0%**
(openrouter_A gemini, 0/18, CI [0%, 17.6%] — every one of the 9 run-1-wrong
gemini cells in that arm stayed wrong on both repeats) to **34%**
(openrouter_A qwen, 39/116, CI [25.7%, 42.6%]). The full per-model table is
in the CSV; the pooled-arm numbers above should not be read as "the" flip
rate — model identity drives more of the variation than arm does.

At the cell level (rather than the run-attempt level): of the 895 cells that
had at least one replicate scored, **170 (19.0%)** flipped to correct on at
least one of the two repeats, and 70 flipped on *both* repeats (i.e.
`cells_flipped_both` summed across `flip-rates-by-arm.csv`: 26 + 35 + 9). Put
differently: roughly 1 in 5 run-1 "incorrect" classifications in this study
was not a stable failure — a second attempt at the identical frozen prompt
was enough to flip it to correct at least once.

## 4. What the run2-vs-run3 data can and cannot establish about the Vertex deviation

This is the section SPEC.md requires to quantify the cost of the protocol
deviation: 91 of the 93 scored `openrouter_B`/gemini cells (46 distinct
questions) were served by Google Vertex with `temperature` silently dropped;
2 (1 question, both runs) were served by AI Studio at genuine
`temperature=0`. Every gemini cell in `openrouter_A` and `tailscale_A` ran at
genuine `temperature=0`.

There are two ways to build a comparator for Vertex-gemini in this dataset,
and they answer *different* questions. Neither one, by itself, isolates a
pure temperature effect. Both are shown below, each labeled with what it can
and cannot support. **A single "is it detectable, yes or no" framing invites
exactly the kind of overcompressed summary this section is trying to avoid —
so this report deliberately does not give a yes/no verdict.**

### 4a. Cross-condition comparator: Vertex-gemini (openrouter_B) vs gemini at temperature=0 in openrouter_A / tailscale_A

This is the most intuitive comparator — "gemini under Vertex" vs "gemini
under real temperature=0" — but it is **confounded**: `openrouter_A`,
`openrouter_B`, and `tailscale_A` are different prompt/retrieval conditions,
not just different temperature regimes. DEVIATIONS.md states this exact
confound in its own words: *"Folding provider sampling noise into that
measurement means a gemini A-vs-B comparison now contrasts two sampling
regimes, not two prompt conditions."* Any difference (or lack of one) in the
numbers below could be driven by the condition change, the temperature
change, or both, at any sample size — more data would not fix this, because
the confound is structural, not a power problem.

| Slice | Flips / attempts | Flip rate | 95% Wilson CI |
| --- | --- | --- | --- |
| openrouter_A gemini (temp=0, condition A) | 0 / 18 | 0.0% | [0.0%, 17.6%] |
| tailscale_A gemini (temp=0, RAG condition) | 2 / 26 | 7.7% | [2.1%, 24.1%] |
| **Pooled temp=0 gemini (A + ts_A)** | **2 / 44** | **4.5%** | **[1.3%, 15.1%]** (anchored by openrouter_A's small-n 0/18 — fragile) |
| openrouter_B gemini, **Vertex-served** (condition B) | 12 / 91 | 13.2% | [7.7%, 21.6%] |
| openrouter_B gemini, AI-Studio-served (condition B) | 2 / 2 | 100% | [34.2%, 100%] (n=2, uninformative) |
| openrouter_B gemini, all (SPEC's 93) | 14 / 93 | 15.1% | [9.2%, 23.7%] |

Read this table as "condition A/RAG vs condition B", not as "temperature=0 vs
Vertex" — the two are entangled here by construction.

### 4b. Same-arm comparator: Vertex-gemini vs its own arm-mates, all within openrouter_B

This comparator holds arm/condition fixed and only varies model (all four
models below ran the identical `openrouter_B` prompt condition; three of the
four — gemma, qwen, glm — ran at genuine `temperature=0`). It removes the
condition confound from 4a, at the cost of introducing a different one: it
now compares *across models*, so any position gemini takes in this range is
as much a statement about "how deterministic is this model in general" as
about temperature. Figures are taken directly from
`flip-rates-by-arm-model.csv` (no new computation):

| Model (openrouter_B) | Flips / attempts | Flip rate | 95% Wilson CI | Temperature |
| --- | --- | --- | --- | --- |
| gemma | 21 / 458 | 4.6% | [3.0%, 6.9%] | temperature_0 |
| glm | 29 / 222 | 13.1% | [9.3%, 18.1%] | temperature_0 |
| **gemini, Vertex-served only** | **12 / 91** | **13.2%** | **[7.7%, 21.6%]** | vertex_default |
| gemini, all (incl. 2 AI-Studio) | 14 / 93 | 15.1% | [9.2%, 23.7%] | mixed |
| qwen | 56 / 284 | 19.7% | [15.5%, 24.7%] | temperature_0 |

On this comparator, Vertex-gemini's flip rate (13.2%) sits essentially
tied with glm (13.1%, both at genuine temperature=0) and below qwen (19.7%,
also temperature=0) — squarely inside the range its own temperature-0
arm-mates span (4.6%–19.7%). It is not the high outlier, nor the low one.

**What 4b does and does not establish.** It shows Vertex-gemini's flip rate
falls within *normal between-model variation* observed elsewhere in this
dataset at genuine temperature=0 — a real and useful fact. It does **not**
show that temperature had no effect on gemini specifically, because gemini is
only compared against *other models*, never against itself under a different
temperature. The one comparator that would isolate a pure within-model
temperature effect is Vertex-gemini (13.2%, n=91) vs AI-Studio-gemini (100%,
n=2) — and that comparison is uninformative on its face (n=2).

### Agreement rate: the same two comparators, restated with rank

`run2-vs-run3-agreement.csv` gives the same picture from a different angle —
whether the two repeats picked the *same letter*, independent of which
letter is correct:

| Slice | Agree / both-scored | Agreement rate | 95% Wilson CI |
| --- | --- | --- | --- |
| openrouter_B gemma (temp=0, same arm) | 207 / 229 | 90.4% | [85.9%, 93.6%] |
| openrouter_A gemini (temp=0, cross-condition) | 8 / 9 | 88.9% | [56.5%, 98.0%] |
| **openrouter_B gemini, Vertex-only (same arm)** | **39 / 45** | **86.7%** | **[73.8%, 93.7%]** |
| openrouter_B glm (temp=0, same arm) | 90 / 111 | 81.1% | [72.8%, 87.3%] |
| tailscale_A gemini (temp=0, cross-condition) | 10 / 13 | 76.9% | [49.7%, 91.8%] |
| openrouter_B qwen (temp=0, same arm) | 109 / 142 | 76.8% | [69.2%, 82.9%] |
| openrouter_B gemini, AI-Studio-only (same arm) | 1 / 1 | 100% | [20.7%, 100%] (n=1, uninformative) |

Ranked against the six informative comparators above (excluding the n=1 row),
Vertex-gemini's 86.7% is **3rd highest overall** — behind only openrouter_B
gemma (90.4%) and openrouter_A gemini (88.9%) — and, restricted to the
same-arm comparator set of 4b (gemma/qwen/glm/gemini, all within
`openrouter_B`), it is **2nd of 4**, above both of its temperature-0
arm-mates qwen (76.8%) and glm (81.1%). Either way, this metric ranks it
solidly in the *upper* half of its comparators, not as an outlier low-end
result — a stronger statement than "does not stand out as an outlier."

### What can and cannot be concluded

- **4a (cross-condition)** shows a ~3x higher flip-rate point estimate under
  Vertex (13.2–15.1%) than pooled temperature=0 gemini elsewhere (4.5%), with
  overlapping but not fully coincident CIs. This comparator is confounded
  with the arm/condition change per DEVIATIONS.md, so it cannot attribute
  that gap to temperature specifically — condition, temperature, or both
  could be driving it, and the 4.5% baseline itself is fragile (anchored by a
  small-n 0/18).
- **4b (same-arm)** shows Vertex-gemini's flip rate and its agreement rate
  both fall inside the range spanned by its own temperature=0 arm-mates —
  on flip rate it's tied with glm and below qwen; on agreement it ranks 2nd
  of 4, above qwen and glm. This comparator removes the condition confound
  but introduces a model-identity confound instead, and it is model-to-model,
  not gemini-to-gemini.
- **The one clean within-model, within-condition contrast** — Vertex-gemini
  vs AI-Studio-gemini, both in `openrouter_B` — exists in principle but has
  n=2 on the AI-Studio side and is uninformative.
- SPEC's own pre-authorization probe (three repeats of one frozen Vertex
  request returning `['b', 'c', 'b']`) remains direct qualitative evidence
  that Vertex sampling noise is real at the individual-request level.

**Plainly stated: this dataset cannot isolate the temperature effect in
either direction.** It cannot demonstrate that the Vertex deviation degraded
determinism beyond ordinary between-model and between-condition variation,
and it cannot demonstrate that it didn't. Every comparator available here is
confounded with either condition (4a) or model identity (4b); the one
unconfounded comparator is underpowered (n=2). **Do not report a gemini_A vs
gemini_B contrast, in either direction, as evidence about temperature without
restating this limitation.**

## 5. What the flip rate implies for the published run-1 accuracy figures

Interpret with the asymmetry from §1 in mind: this study only measured the
wrong→right flip direction (5102 correct run-1 cells were never repeated), so
it cannot produce a symmetric noise estimate or a corrected accuracy number.
What it does show:

- Roughly 13–19% of individual repeat *attempts* on a run-1-wrong cell come
  back correct, and about 19% of run-1-wrong *cells* flip on at least one of
  two repeats. That is a non-trivial fraction of the questions counted as
  "model failures" in the run-1 tally — for at least some of them, a
  differently-sampled attempt at the identical frozen prompt would have
  scored them correct.
- This does **not** mean the "true" per-arm-model accuracy is 13–19% higher
  than published. It means the published run-1 accuracy number is a
  single-draw estimate with real sampling noise beyond what a
  question-count-only binomial CI would suggest, because at least part of
  each model's error set is not a stable, reproducible failure mode but a
  probabilistic outcome that could have landed on either side of correct.
  Without the mirror-image right→wrong flip rate (not measured here), the
  net effect on the reported accuracy point estimate is unknown in sign as
  well as magnitude — a full accuracy-noise model would need that other
  half.
- Practically: treat published run-1 per-arm-model accuracy figures as
  having a wider effective error bar than the binomial-over-500-questions CI
  implies, and treat any single incorrect-cell list from run 1 as containing
  a meaningful fraction of resampling noise rather than pure, stable model
  failures. If a downstream analysis depends on *which specific questions*
  a model got wrong (not just the aggregate rate), this instability is a
  bigger problem than if it only depends on the aggregate accuracy number.

## 6. Limitations

- **8 missing cells (logical calls).** All 8 are exhausted at the 5-attempt
  ceiling per SPEC: `openrouter_B` gemini n012 (r2+r3), n036 (r2+r3), b326
  (r2+r3), b373 (r2 only); `tailscale_A` glm b264 (r2 only). These are
  excluded from every denominator here rather than imputed. They represent
  0.45% of the 1796 frozen logical calls (8/1796) — small, but not zero, and
  concentrated in `openrouter_B`/gemini (7 of 8), which is already the
  heterogeneous-upstream slice.
- **Replicate completeness.** Of the 898 run-1-incorrect cells, 893 have both
  run 2 and run 3 scored, 2 have only one replicate scored (b373: r3 only;
  b264: r3 only), and 3 have neither (n012, n036, b326 — all
  `openrouter_B`/gemini). The 3 fully-missing cells contribute nothing to any
  metric in this report; the 2 single-replicate cells contribute to the
  flip-rate tables (their one scored run) but cannot contribute to the
  run2-vs-run3 agreement table, which requires both runs.
- **gemini_B heterogeneity.** As detailed in §4, the `openrouter_B`/gemini
  slice mixes 91 Vertex-served (temperature dropped) and 2 AI-Studio-served
  (genuine temperature=0) scored attempts. Every number in this report that
  touches `openrouter_B`/gemini is either stratified by upstream or
  explicitly flagged `mixed`/`temperature_0` in the `temperature_regime`
  column of the CSVs. No CSV row pools Vertex and non-Vertex gemini_B cells
  without a `mixed` flag, and §3's "all arms pooled" headline number is
  explicitly paired with a gemini_B-excluded version for this reason (they
  turn out to be nearly identical — 13.42% vs 13.33% — because gemini_B is
  only 93/1788 = 5.2% of the scored run-attempts, but that near-equality is a
  fact about this dataset's composition, not a license to pool without
  checking in general).
- **Small-n slices.** Several arm x model and upstream-subgroup cells have
  n < 20 (e.g. openrouter_A gemini n=9 cells/18 attempts, openrouter_B
  AI-Studio gemini n=1/n=2, tailscale_A glm n=19/39). Wilson intervals for
  these are wide, and any single-slice point estimate should be read with
  that in mind — several of the "trends" described in §4 are point-estimate
  differences inside overlapping intervals, not confirmed effects.
- **Clustering / non-independence**, as described in §2: cells differ in
  intrinsic difficulty, and a cell's two repeats are not independent draws
  in the way two different cells are. All confidence intervals in this
  report should be read as approximate.
- **Correctness definition.** All flip/correctness figures use
  `strict_correct` from the `scores` table (the same field used to select
  the 898 run-1-incorrect cells in the first place), not `lenient_correct`.
  This keeps the flip measurement consistent with the criterion that put a
  cell into the replicate pool.
